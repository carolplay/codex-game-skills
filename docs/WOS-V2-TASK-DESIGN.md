# WOS V2 任务设计与实施安排

## 故障归属

本轮偏差来自任务规格及批处理设计，不是已发现的CrossMacro点击回放偏移。直接Python批处理打开了正确VIP页面，OCR识别到“领取”；但 `wos-vip-inspect.json` 只定义冷却倒计时检查，没有可领分支，符合实际状态的页面仍被判失败。私有批处理在捕获任一任务异常后执行 `break`，未做页面恢复，因而阻断后续任务。

六项宏名义上已经都是主城进入、主城结束；缺的是**所有已知业务分支都能结束，以及异常后可验证的固定退出流程**。仅在每个宏开头写“从主城开始”，不能将上一项遗留的VIP页自动变成主城。

## 六项任务现状

| 任务 | 当前操作 | 已有回放证据 | 缺口 |
|---|---|---|---|
| 邮件 | 报告/系统/联盟批量已读领取；有奖励才关弹层；返回主城 | 无新奖励分支；跨角色系统邮件奖励分支 | 其他新奖励分支继续积累；缺任务级异常退出 |
| VIP | 主城进入、验证免费礼包冷却、返回 | 已领冷却 | 缺可领分支及对应退出；宏不是完整VIP领奖任务 |
| 探索挂机 | 领取挂机收益、验证奖励及灰态；不可领时跳过 | 真实领取与冷却 | 不同角色/异常弹窗覆盖；缺失败后的固定退出 |
| 免费体力餐 | 进入丰盛的招待；领取或识别下次补给；返回 | 冷却分支；真实领取只有人工证据 | 宏可领分支现场验收 |
| 学院补给 | 从概览按文字进入；领取免费补给或识别冷却；返回 | 冷却分支；真实领取只有人工证据 | 宏可领分支及角色列表差异验收 |
| 联盟 | 查看互助；领取战利品/盟友赠礼；返回 | 空奖励分支；真实礼物只有人工证据 | 礼物可领分支验收；互助当前仅查看，不自动帮助 |

训练、情报、竞技场、采集等尚未列入上述固定宏清单。游戏任务资料只是开发候选池；执行agent不扫描未覆盖日常。

## 可组合任务契约（待实现）

每个任务描述自己的入口、业务分支、成功出口、偏差退出路径和结果证据。首版统一采用**主城**作为任务之间的交接界面。主城与野外是不同锚点；将来野外任务可声明独立入口，但跨界面转换必须是已验证宏，不能靠推断。

| 字段 | 含义 |
|---|---|
| `entry_anchor` | 本任务要求的初始界面，首版为主城；通过多个文字/图像条件确认 |
| `identity_policy` | 切号后与每项任务开始前核验领主及王国；不把页面核验替代身份核验 |
| `branches` | 可领、已领/冷却、无收益、未解锁和未知状态分别描述；未实现分支记偏差 |
| `success_exit` | 成功或正常无收益后回主城，必须有本地确认 |
| `deviation_exit` | 仅关闭本任务已知页面/弹层并返回主城；有限步数和超时 |
| `postcondition` | 是否有领奖证据、是否冷却、是否恢复锚点；分别记录 |
| `result` | 业务结果、失败步骤、退出结果、证据路径及是否允许继续下一项 |

“后退”是一种动作，不是已确认的界面。退出路径应按当前已识别页面执行，例如 VIP→主城，奖励层→邮件→主城；不盲按多次后退、不关闭未知弹窗、不重复领取。主城入口固定不等于主城地图中建筑位置固定，建筑入口仍优先采用稳定菜单或本地文字定位。

预定义退出仅恢复交接界面，不继续失败任务、不补领取、不修宏。退出流程也是本地宏步骤，不增加中途agent调用。

## 结果与继续条件

| 结果 | 例子 | 后续 |
|---|---|---|
| `completed` | 奖励证据成立 | 确认主城后继续 |
| `no_action` | 有证据的冷却、空奖励、未解锁 | 正常结束，不记为领奖；确认主城后继续 |
| `deviation` | 合法页面但业务分支不支持，或结果断言不成立 | 记录偏差；固定退出成功且身份/环境仍可信后继续 |
| `fatal` | 错号、锁屏、权限拒绝、尺寸变化、失去执行权 | 停整轮，不尝试恢复游戏输入 |
| `anchor_unrecovered` | 未知页面、退出超时或主城无法确认 | 停整轮，余项记未执行 |

冷却“跳过”不等于遇错；业务偏差也不应自动变成全局失败。只有确认交接锚点、身份及环境仍有效，才能将任务级偏差隔离。

## 实施顺序与验收

| 顺序 | 工作 | 验收标准 | 当前状态 |
|---|---|---|---|
| 1 | 定义任务结果与固定起止/退出契约 | 日志分别记录业务结果和锚点恢复；区分任务偏差与全局停止 | 本文已明确；代码未实现 |
| 2 | 完善VIP状态分支与已知页面退出 | 可领、冷却、未知三分支；未知不点领取；所有可恢复结果回主城 | 待开发 |
| 3 | 批处理增加固定退出与继续能力 | 注入一项业务失败，确认回主城后下一项仍执行；错号/权限等仍停全局 | 待开发 |
| 4 | 让六项宏满足同一契约 | 所有已知正常分支可回主城；未知页面有限停止 | 待开发/逐项回放 |
| 5 | 验证组合与跨角色适配 | 相同身份环境下打乱六项顺序；至少两种角色配置通过；分别保留分支证据 | 待测试 |
| 6 | 多账号串行执行 | 切号与关闭登录弹窗作为独立准备流程；先核身份再交给任务批处理；不并发控制单窗口 | 待开发 |
| 7 | 恢复排程前验收 | 未锁屏及自然闲置锁屏实测，独立后端单独验收；按当前角色数量验证整批耗时 | 未通过；定时继续暂停 |

优先解决组合边界，再扩展覆盖项目。这个顺序避免继续增加只能在某个历史状态运行的长脚本。本文发布不代表启用这些能力，也不授权启动下一轮游戏操作。

## 单轮输出

agent最后一次汇总只检查固定清单。每项记录预期、实际、分支、奖励证据、退出结果、耗时和证据路径；剩余未执行项目说明阻断原因。准备、宏执行、最终检查分别计时；宏内部模型调用与整轮agent调用分别统计。宏失败但退出成功仍是业务偏差，不能改写为任务完成。
